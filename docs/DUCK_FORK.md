## The rule this fork follows

**Change nothing we cannot measure.**

The harness needs a 96 GB card and a 27B FP8 model, so we cannot run it
locally, which means we cannot A/B a change to its prompts, sampling, tools or
model before submitting. Tufa Labs' own numbers show why that matters: the same
submission scored between 0.77 and 1.30 on the leaderboard, and 1.6002 ± 0.4475
across the 25 public games. Against noise that large, an unmeasured "improvement"
is indistinguishable from a coin flip, and a coin flip on a leaderboard-verified
solution is a bad trade.

So every change below is a **guard**: it either prevents losing a run outright,
or makes a failed run diagnosable. Verified by
`scripts/build_duck_notebook.py`'s own checks plus an explicit audit — the only
assignment this fork adds to the benchmark is `target.max_runtime_s`, and it is
inside `if not TRUE_SUBMISSION`, so the scored run never sees it.

## The four changes

### 1. Soft deadline for the scored run — the one that can save the whole run

Upstream's run cell:

```python
soft_end = None
if not TRUE_SUBMISSION:
    budget = float(getattr(target, "max_runtime_s", 0.0) or 0.0)
    if budget > 0:
        soft_end = ...
```

The scored run gets **no deadline at all**. It relies on the benchmark's own
per-game limits landing inside Kaggle's 9-hour cap. That holds for the public
game set; the hidden set is a different size and a different difficulty, and if
it runs long, Kaggle kills the notebook. **A killed notebook emits no
`submission.parquet`, so the run scores nothing** — not a reduced score, no
score, however well the games actually went.

The fork adds an `else` branch setting `soft_end` to 8 hours after notebook
start, leaving an hour to wind down, write artifacts and let the gateway emit
the submission file.

This is asymmetric on purpose. If the run would have finished anyway, the
deadline never fires and nothing changes. It only acts in the case that would
otherwise have lost everything. And it changes a *value*, not a mechanism:
`soft_end_time` is the same parameter upstream passes on every interactive run.

### 2. Preflight gate — fail in one minute instead of eight hours

Three ways to lose a run that upstream does not check for:

- **The wrong GPU, silently.** Measured in this project
  (`docs/superpowers/experiments/kaggle-env-probe.md`): Kaggle's push API reads
  the accelerator from the CLI flag, not from notebook metadata, and an
  unrecognised value is ignored without warning — pushing with `nvidiaRtx6000`
  produced a Tesla P100. A 27B FP8 model does not fit that card. The first
  symptom would be a bad leaderboard score, days later.
- **An input that did not mount.** Kaggle attaches datasets asynchronously and
  a freshly created kernel's first run can start before they finish.
- **No GPU at all**, which surfaces as a missing `nvidia-smi` rather than as an
  error.

The gate checks the GPU name and VRAM (refusing anything under 40 GB), and that
every attached input actually exists on disk. It runs after the mount-resolution
cell and before the multi-GB setup commands, so it costs about a second and
fails before anything expensive happens.

### 3. Bounded verification pass — test without spending a submission

Upstream's Save & Run All plays the competition's bundled environments
**offline**, with the real solver and no gateway. That makes it a genuine
end-to-end test of the whole pipeline that costs no submission — but at the full
notebook budget it takes hours.

The fork sets `target.max_runtime_s` on the non-submission path only, which is
the attribute upstream already derives its soft end from. The verification pass
finishes in about half an hour; the scored rerun takes the other branch and is
unaffected.

### 4. Adaptive per-game time budget — derived from a measurement, not a guess

The score is the **mean over games**, so a game that never gets played scores 0
and drags the mean exactly as hard as one played badly. That makes an unplayed
game the most expensive outcome available, and upstream's fixed per-game budget
is what produces them.

Measured in this fork's own verification run on Kaggle hardware:

```
Model loading took 33.66 GiB memory and 160.8 seconds
Available KV cache memory: 43.62 GiB -> GPU KV cache size: 177,968 tokens
generated tokens/sec: 179.75 (job wallclock)
manifest: max_runtime_s_per_game=7920.0, concurrency=28
```

Tufa Labs' reference run used ~59k tokens per game. At the ~180 tokens/second
this hardware sustains end to end, 110 hidden games need about **10 hours**
against Kaggle's **9-hour** limit — and games run in waves of
`solver.concurrency`, so a fixed budget lets the early waves take everything
and leaves the last wave unplayed.

The fork therefore derives the budget: split the time that actually remains
across the waves actually needed, and **never raise it above what upstream
asked for**. If the run would have fitted anyway, nothing changes; the change
only ever divides a budget that would not have fitted.

```python
_waves = ceil(len(bm.games) / bm.solver.concurrency)
_per_game = ((soft_end - now).total_seconds() / _waves) * 0.9
if _per_game < bm.solver.max_runtime_s_per_game:
    bm.solver.max_runtime_s_per_game = _per_game
```

### 5. Run manifest

Upstream prints its preamble but not the resolved shape of the run. The fork
prints the game count, per-game budget, pass count, solver class and the
submission flags. Without it, a low score and "played four games, then got
killed" look identical in the logs.

## A change that looked obvious and was measured to be worthless

Worth recording, because it is the method working as intended.

The bundle's setup command launches the server with `VLLM_MAX_MODEL_LEN =
65536` while the agent's own `ANALYZER_CONTEXT_WINDOW` is `32768` — twice the
context the agent ever uses. vLLM's own startup line looks like a smoking gun:

```
Maximum concurrency for 65,536 tokens per request: 10.12x
```

Halving `max_model_len` would double that figure, so it reads as free
concurrency. It is not. The same run's engine logs show peak KV cache usage of
**76% across 25 concurrent requests**, which puts the *actual* average context
at roughly 5,400 tokens — nowhere near 32k, let alone 65k. The KV pool is
allocated as a whole and is not the binding constraint, so lowering
`max_model_len` would change nothing.

Not shipped. The remaining serving question — what concurrency this specific
card actually prefers, given generation throughput fell from 454 to 160
tokens/second as the cache filled — is empirical, and answering it needs a
measurement run per setting rather than an argument.

## What this fork deliberately does not do

- No prompt changes.
- No sampling changes (`temperature`, `top_p`, `top_k` untouched).
- No tool or model changes.
- No change to game selection, pass count or weighting — upstream sets
  `bm.games`, `bm.n_passes = 1` and `bm.game_weights = None` in its run cell,
  after our hook, and we leave that alone.

Each of those is a plausible improvement. None is measurable before submitting.

## Expected score, honestly

**We cannot guarantee ≥1.00.** Tufa Labs' own data: best leaderboard 1.21, same
submission as low as 0.77, public-set spread ±0.4475. Our guards remove ways to
score *zero*; they do not raise the ceiling.

The one real lever on reliability is the number of attempts. With three
submissions from three accounts, run independently, the leaderboard keeps the
best. Treating the score as roughly normal around 1.2 with a standard deviation
of 0.4, a single run falls below 1.00 about 30% of the time — but all three
doing so is about 3%. **Best-of-three is what turns "probably" into "almost
certainly", and it is the reason to spend all three slots rather than iterate
on one.**

## Reproducing

```bash
kaggle kernels pull jeroencottaar/tufa-labs-duck-harness-june-30-milestone-winner -p reference/duck -m
python scripts/build_duck_notebook.py
kaggle kernels push -p notebooks/duck --accelerator NvidiaRtxPro6000
```

The build script locates cells by content and refuses to run if upstream's shape
has changed, so it fails loudly rather than silently producing a notebook
missing its guards.
